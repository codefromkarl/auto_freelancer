# BidMaster 架构设计（Manual Pipeline）

## 架构概述

BidMaster 采用 **Python FastAPI + SQLite + 手动流水线脚本** 的执行模式：

- `python_service/` 提供 API、业务服务、数据模型
- `scripts/manual_pipeline/` 提供抓取、评分、复核、投标 CLI 流程
- `python_service/data/freelancer.db` 作为本地状态与投标记录存储

## 分层

1. API 层：`python_service/api/*`
2. 服务层：`python_service/services/*`
3. 数据层：`python_service/database/*`
4. 执行层：`scripts/manual_pipeline/*`

## 核心数据流

1. `02_fetch.py` 抓取项目并入库
2. `03_score_concurrent.py` 打分并写回项目
3. `04_review.py` 输出候选项目报告
4. `05_bid.py` 冻结最终提案与报价，通过 QQ Bot 请求内容审批；显式启用的执行器核验后提交同一份内容
5. 在外部提交前，`bid_submissions` 表提交唯一项目预留记录。确认成功后与 `bids` 记录一起更新；异常保留预留记录并标记 `outcome_unknown`。
6. `projects.status` 标记本地状态（如 `bid_submitted` / `skills_blocked`），调度器同时排除有提交预留记录的项目。

## 运行方式

- 直接本地运行脚本
- 或通过 `docker-compose` 运行 `python_service` 容器

## 设计原则

- Fail-Closed：任何关键校验失败必须阻断提交
- 防重提交：`bid_submissions.project_freelancer_id` 唯一约束覆盖并发 API/CLI 请求；`submitting`、`outcome_unknown` 和 `submitted` 均阻断再次提交，不能因超时或缺少 ID 自动重试。旧版缺 ID 的成功审计记录同样阻断。
- 远端优先：投标前强制远端状态校验，避免本地陈旧状态误投

## 提交契约

- 所有业务 API 在主应用注册时统一验证 `X-API-Key`，`BYPASS_AUTH` 不再生效。`/health`、根入口和 API 文档保留公开访问。
- `create_bid` 不提供跳过内容检查或远端状态检查的参数。默认生成经过校验的最终文案，不自动提交来源不明的缓存草稿；显式文案同样经过服务校验。
- 文案长度使用 `PROPOSAL_MIN_LENGTH` / `PROPOSAL_MAX_LENGTH`，并校验与提交报价的关系。修改投标文案也需校验。
- `amount` 默认表示项目本币金额；美元建议价必须显式传入 `amount_currency="USD"`。不通过数字是否恰好等于建议价推断币种；不再自动美化金额。
- 提交超时、响应缺少有效 ID 或本地落库失败返回错误，不宣称成功。预留记录持续阻断提交，直到人工核对远端结果。当前不提供自动重发或自动解锁功能。
- 新增表由现有 `init_db()` 建表机制创建。本轮只在隔离测试库验证，业务库变更属于后续授权的部署/迁移步骤。

## 本地验证

本轮验收与证据见 [可靠性优化清单](../plans/2026-10-10-reliability.md)。测试使用虚拟凭证和临时数据库，外部 HTTP 调用被拦截。

项目详情 API 默认读取缓存，显式 `refresh=true` 或缓存缺失才访问远端；该读取策略不影响真实投标前的远端门禁。消息数据在数据库会话内转换为响应数据，避免提交后属性过期。前端所有写操作均不自动重试，未知结果需要人工确认。

## 初筛与评分数据契约

- 搜索请求包含完整描述和技能详情；详情与搜索共用字段落库逻辑，保存全文、技能名称、竞争数据及实际返回的客户资料。缺失客户数据保持未知。
- 能力匹配读取全文和技能名称；短词按词边界匹配。简历技能分组 ID 不能冒充 Freelancer 平台技能 ID，账号资格需与真实登记技能单独核对。
- fixed 类型、预算/币种或汇率未知时不直接通过初筛；计入相应排除原因，等待核实。远端同步失败会向调用方抛出错误，不能以旧本地记录报告抓取成功。
- 评分、复核、通知及调度按远端 `submitdate` 判断发布时间，支持秒、毫秒、ISO 时间；不以本地入库时间冒充新项目。
- LLM 评分使用全文、实际年龄与竞争信息。分数为启发式排序，权重是配置偏好，没有中标概率含义。
- `LLMScoringConfig.generate_proposals=False` 可先完成评分再逐项复核；零重试配置只进行一次模型尝试。评分失败时 CLI 返回错误码。
- 建议报价在数据库保持 USD；传入提案生成的报价换算为项目本币。汇率来自 Frankfurter 当前 v1 地址，无法核实汇率时应等待核验。

本轮真实样本与后续预览见 [筛选复核验收](../plans/2026-10-10-filter-review.md)。

## QQ 通知与受控提交契约

- QQ 鉴权与 Gateway 接收器独立于 Freelancer 凭证。私聊/群聊只向显式配置的接收对象通知，只接受允许的 OpenID 审批；`身份` 仅回复当前用户身份，不自动授权。
- `qqbot.db` 保存不可变审批快照、事件去重、通知回执和每日额度；它与业务数据库分开。完整文案、账号、项目版本、报价、币种、工期和目标对象均受内容摘要保护，批准有效期默认 30 分钟。
- API 创建投标、CLI 和调度器共用 `submit_approved_bid`；默认 `BID_SUBMISSION_ENABLED=false`，真实模式必须同时具备有效的 QQ 内容审批。批准后不再生成文案。
- 客户资料、账号资料完整度及剩余投标额度尚无法完全自动核实，必须通过 `批准风险` 人工复核。执行前再核对当前账号、技能、远端需求和报价工时约束。受控默认每日 1 次投标尝试、20 个评分项目；这不是精确的模型费用预算。
- 项目需求、预算、币种、技能或客户标识变化会清除旧评分、报价与草稿，旧内容批准也无法通过版本检查。单次抓取全部失败返回错误，不把旧缓存报成新数据。
- 通知和投标先持久预留再调用外部接口，结果不明不会自动重发；需要人工核实。过期后新建快照可重新通知，不能延长旧批准。
- 默认预览循环可抓取、评分和通知，但后台守护、账号投标资格、QQ 实际接收及主动消息权限仍须分别验收。

操作与证据见 [QQ 接入指南](../getting-started/QQBOT_GUIDE.md) 和 [本轮验收清单](../plans/2026-10-12-qqbot-automation.md)。

## 竞争标书与提案评估

候选准备使用 `proposal_competition.ensure_competitor_context` 取得当前账号、项目及币种的竞标快照。缺失或过期会通过既有客户端 GET 刷新，默认最多 8 页、400 条；达到上限明确标为样本不完整。既有竞标表保存数据，`audit_logs` 的 `competitor_snapshot` 记录可见 ID、有效价格 ID、账号、时效及内容摘要，无新增业务表/列要求。撤回、密封、本账号及无效报价不进入价格/正文参考；已失去公开权限的旧正文移除。不同币种及账号的快照不能混用。

生成器读取完整需求及有界竞标上下文：公开报价中位数、工期、需求特征提及数量和最多 6 份各 900 字符的参考片段。竞标正文是不可执行的参考数据，不能替代项目需求、系统指令或本人的真实履历。低价试点/模拟原型单独标注，统计不是同等范围的成交价。

生成后、显式人工稿准备和 `/api/v1/proposals/evaluate` 使用同一评估器。结果包含文案摘要、本币报价/工期、评估版本、竞标快照摘要、价格位置、特征差距、文字重合与复核事项。特征检测只说明文字提及，不能认证质量、履历或中标概率。比中位价高超过 20%、案例表达不足、资料失败/过期或样本不完整都会提示人工复核，系统不自动改价。

硬阻断包括基础内容校验失败，以及除去原始需求共有文字后，与竞争者至少 12 个五词连续片段重合且覆盖本稿片段至少 50% 的大段复制风险。检查是可解释的文字重合启发式，不保证检测所有语义抄袭。生成耗尽重试仍不合格时返回失败，不保存“成功但未通过”草稿。

QQ 与前端展示比较摘要和补充事项；候选的完整文案、评估及报价一起冻结。提交要求当前评估版本，文案/报价/工期摘要匹配，参考数据时效仍有效；市场快照发生变化则重新准备和批准。旧版无评估快照不能用于新提交。`04_review.py` 读取当前快照及同一最终文案的评估记录，陈旧数据显示未知，不显示为零报价。

默认竞标时效 `PROPOSAL_COMPETITOR_CONTEXT_TTL_SECONDS=1800`，同时约束审批有效期。QQ 接收器使用独立的纯展示模块，仍不依赖交易凭证。该功能通过当前生成模型和确定性评估实现，不新增付费裁判模型调用。

验收见 [竞争标书链路计划](../plans/2026-10-12-competitor-proposal-pipeline.md)。

## 统一评分契约（2026-10-12 v2）

- Web `POST /projects/{id}/score`、CLI 和调度器共用 `LLMScoringService`。缺少模型、完整需求、已确认的币种/类型或有效结构化结果时拒绝评分；Web 返回 422，不静默切换规则算法。默认 `LLM_SCORING_MODE=single`，显式配置 ensemble/race 时所有入口使用同一配置。
- 模型必须返回六个 0–10 维度、正整数工时、正的有限美元报价和解释。总分由程序计算；预算效率按报价扣除代码现行普通费用估算的净时薪计算，竞争分为连续拥挤程度/年龄偏好。没有重复小项目加分，也不把低时薪抬高至 10 USD。权重合并 YAML 与数据库，兼容 `tech_match` 名称并归一化。
- `projects.score_metadata` 保存来源、版本、输入/策略摘要、模型、各维度、权重、报价经济性及未知信息；`scored_at` 保存 UTC 时间。`hourly_rate` 是实际建议报价对应的毛时薪；净时薪见元数据。付款验证未确认时保留客户未知，仍需现有人工风险复核。
- 客户、竞争、技能、发布时间及需求预算变化会使旧分失效；策略、模型变化和默认 6 小时 TTL 同样触发重评。缓存包含完整评分载荷及模型/策略，不能跨动态信息复用。旧评分及 `manual`/`rule` 来源可以展示，自动候选要求当前版本的有效 `llm` 评分。
- 调度选择先检查分数有效性及已知报价/工时/客户硬条件，再取前 N 项。准备失败标记在该次评分上并补选；下一次有效重评会清除该标记。单轮准备尝试默认最多 10 次，不改变每日真实提交限制。
- 能力初筛的 AI/媒体等泛词需同时有开发交付上下文；工时规则使用词边界，只有标题明确的局部修复才收窄工作量。规则算法仅作本地参考，不再提供 Web 正式分数。
- 新增元数据列沿用项目 `init_db()` 的幂等兼容迁移；本轮只验证隔离库，尚未对业务库执行。旧评分不会被删除，但启用自动候选前须按新契约重评。分数仍是偏好排序，没有中标概率或中标率提升的验证。

本轮验收见 [投标筛选与评分修复](../plans/2026-10-12-scoring-repair.md)。

## 候选工作流、澄清与观测

- `candidate_workflows` 是本地处理队列，独立于远端 `projects.status`、QQ 批准和 `bid_submissions`。状态为待判断、待澄清、可准备、待审批、暂缓、拒绝、已投标和结果未知；每次变化带原因、再次处理条件及乐观锁版本。人工决定不会被轮询/评分覆盖。批准过期进入手动恢复的暂缓状态，不自动续期、重新生成标书或再次通知。
- 评分契约更新为 v3，可返回最多五个关键范围问题。问题未解决时，不评分重复问题、不抓取全量竞标正文或准备标书。完整答复绑定当前需求摘要并作为操作者提供的信息进入评分/标书上下文；假设不能冒充客户确认。答复使旧评分和报价失效，需重评。需求变化会丢弃过期答复。
- 队列状态和澄清摘要在准备/执行前检查。批准绑定该次候选及澄清摘要；拒绝后恢复不能复用旧批准。QQ 拒绝和真实投标/未知结果由既有权威记录同步，队列 API 不能直接标记已投标或解除未知结果。
- 调度顺序为抓取初筛 → 评分/澄清 → 可行候选选择 → 候选竞争资料 → 标书准备/审批。全量竞标读取只针对本轮可行候选；中标后的观察仍可由原有独立同步工具执行。
- `workflow_events` 记录实际抓取/初筛原因、评分、状态流转、准备、审批、通知和提交核验结果；`workflow_runs` 保存整轮耗时、分阶段耗时和失败阶段。抓取返回空集时不会把旧本地记录算成新抓取；重复关键词的读数是观察条目数，队列按项目 ID 去重。
- 评分模型调用次数在 provider 执行入口计数，与缓存命中分开；只累计已返回的 token 用量，缺失时明确表示不完整，费用保持未知。事件计数可以包含同一项目多次处理，不提供虚构转化率或中标率。已确认提交后的统计落库失败不改变投标成功记录，也不允许自动重发。
- 前端 `/workflow` 提供队列、完整答复、暂缓/拒绝/恢复和最近七天统计。写操作包含队列版本，409 冲突不自动重试；查看/同步队列不发送客户或 QQ 消息。所有新 API 均验证原有 `X-API-Key`。
- 新增三张表沿用 `init_db()` 的建表机制。本轮只在隔离数据库验证，不对业务库建表；正式运行须初始化表并按 v3 重评旧候选。

验收见 [候选队列、澄清与流程统计](../plans/2026-10-12-workflow-queue.md)。
